# Web frontend

Reference for coding agents and maintainers, linked from [`AGENTS.md`](../../AGENTS.md) § Key File Locations. The authorization model and the unsafe-route classification rule stay in `AGENTS.md`; this file holds the URL-group and filter-framework detail.

Lives at `src/findajob/web/`. One file per URL group in `routes/` (e.g. `routes/materials.py`, `routes/board.py`, `routes/landing.py`). Shared partials (`_nav.html`, `_job_row.html`) live in `templates/`.

## Top-level URL groups

- `/config/` — raw text editor for allowlisted config files (`findajob.web.config_files`).
- `/settings/` — domain-aware config editors with per-page UX (validation, structured rows, HTMX partial-swap). Occupants: `/settings/reject-reasons/` (#490), `/settings/active-sources/` (#603 — checkbox list of `REGISTERED_ADAPTERS` with per-row `is_configured()` badge; writes `config/active_sources.txt` atomically), `/settings/connections/` (#614 — maintenance UI for `data/connections.csv`: last-imported timestamp, row count, refresh/replace, remove with confirm-zone modal mirroring the #700 regenerate-confirm pattern), `/settings/backup/` (#841 — one-click backup tarball download; streams a gzipped tar via `sqlite3 .backup` API + `tarfile`; tarball follows the `state/` contract in `docs/operations/restore.md`; it leaves out every file in `findajob.env_file.SECRET_STATE_FILES` and clears the `onboarding_sessions` API keys in its database copy (`session_store.clear_stored_keys`), and restore keeps the target's own copies of those files and clears those keys in the restored database; every instance gets its own backup), `/settings/timezone/` (#988 — IANA zone picker that atomically writes `data/timezone` via `findajob.timeutil.write_timezone_file`; pick takes effect on next restart, mirroring the onboarding pick and the dashboard restart-to-apply banner #981; the dashboard timezone banner links here), and `/settings/feed-urls/` (#985 — verify-only view of the configured ATS feeds; a "Verify feed URLs" button probes each Greenhouse/Lever/Ashby slug for live/dead/unreachable/unsupported (404 = dead, 5xx/429/timeout/network = unreachable; 8s per-feed timeout, run concurrently) and renders a plain-language reason per row, via the shared `findajob.fetchers.feed_probe` helper (#1023, also used by #983/#984); the pre-Verify listing is display-only — company/ATS/status appear on Verify — because the shared helper couples parse+probe; editing the feed list stays in the raw `/config/` editor, which coexists). The connections page shares `findajob.web.connections_upload` (validator + atomic write) with the onboarding gate at `/onboarding/connections/` (#571) so the two upload paths can't drift; the shared `templates/settings/_linkedin_export_explainer.html` partial keeps the LinkedIn-export procedure copy DRY across both. Saves take effect on the next request without container restart; `findajob.config_loader` loaders are no-cache. The `/board/dashboard` shows a dismissible banner when `active_sources.txt` is absent, pointing at `/settings/active-sources/`. All `/settings/` pages include the shared `templates/settings/_settings_nav.html` sub-nav (#988) — a single declarative `(href, label)` list that cross-links every settings page and bolds the active one via a `request.url.path` prefix match. There is no `/settings/` index route; the sub-nav is the discoverability surface. Adding a settings page = append one pair to that list and include the partial in the new template.
- `/onboarding/` — first-run NUX. Steps: (0) auth credentials (#895 — conditional, only when `FINDAJOB_AUTH_USER`/`FINDAJOB_AUTH_PASS` not set; writes to `data/.env` + `app.state`, middleware activates immediately without restart), (1) API keys (user's own OpenRouter required; written to data/.env and the process environment, never to the database), (2) chat interview (`onboarding_sessions` table). Sentinel `data/.onboarding-complete` written by the Gmail-config gate; `findajob.web.onboarding_guard` guards the core app surfaces (board, materials, stats, all `/settings/*`, speculative, rejections-review, landing, notifications), redirecting them to `/onboarding/` until it exists; `/onboarding/`, `/docs/`, `/config/`, `/tools/`, and `/ingest/` stay reachable. Alternative path: `/onboarding/restore/` (#841) accepts a backup tarball upload, validates the `state/` contract, extracts atomically with rollback, and redirects to the dashboard — skipping the interview. Confirm-overwrite gate on already-onboarded instances.
- `/docs/` — renders pages from `docs/getting-started/*`, `docs/usage/*`, `docs/operations/*`, `docs/troubleshooting.md` inline. Slug allowlist in `findajob.web.routes.docs._PAGES`. Breadcrumb navigation on subpages, sequential "Next step" links on getting-started pages, primary CTA on the index.
- `/tools/` — guided LLM prompts (`findajob.web.tools_registry`) plus direct-edit shortcuts. Each prompt tile loads its body from `config/tool_prompts/{slug}.md` and renders a Copy-prompt button plus an "Open in Claude" anchor pointing at `claude.ai/new?q=<urlencoded prompt>` (anchor is omitted when the encoded prompt exceeds 6 KB). Adding a new tool = append a tile to `TILES` + drop a markdown file in `config/tool_prompts/` — no schema, no migration. Prompts steer their output into gitignored `candidate_context/profile.md` sections (`## Excluded Categories`, `## Title Calibration Notes`, etc.) rather than tracked role files, keeping the surface generalization-safe (#150).

## Row fade-out

A board row that leaves the table tints for its outcome, then fades out, instead of vanishing when the response lands. The server names the outcome in the `X-Row-Outcome` header (routes and values: [`board-lifecycle.md`](board-lifecycle.md)). `static/row_fade.js` listens for `htmx:beforeSwap` on `document.body`; when the swap target is a `<tr>` and the header is present, it sets `data-row-outcome` on the row and overrides the swap to `outerHTML swap:<n>ms` through `detail.swapOverride`. htmx adds `htmx-swapping` for that delay, and `static/app.css` does the rest: a tint per outcome (`rejected` light red, `waitlisted` light yellow, `applied` and `flagged` light green) and an opacity transition. Responses without the header swap as before, so only rows that leave are delayed.

- **Duration** is the `--row-fade-ms` custom property in `app.css` (default `500ms`). The script clamps it to 300–1000 ms and falls back to 500 ms when it cannot parse the value. The delay is the fade time; there is no JS timer.
- **`prefers-reduced-motion: reduce`** turns the transition off and keeps the row at full opacity. The tint stays for the 300 ms minimum.
- The listener is tied to `<tr>` targets, so action cells that swap a `<td>` or a modal are unaffected.

## Per-column filter framework

Declarative framework at `findajob.web.filters`. Each board tab declares a `tuple[ColumnSpec, ...]` in `findajob.web.filters.registry`; framework parses URL params, builds parameterized SQL clauses, and renders header inputs via shared partials.

URL contract — flat, type-suffixed param names: `?col=sub` (TEXT), `?col_min=&col_max=` (SCORE/INTEGER), `?col=a,b,c` (ENUM), `?col_from=&col_to=` (DATE), `?sort=col&desc=1`, `?cols=a,b,c` (visibility and order).

The page URL is the only URL the address bar may hold (#1218). Filter inputs fetch `/board/<tab>/rows`; that route sends `HX-Push-Url: /board/<tab>?<query>` when the swap targets `#rows`, and 303-redirects to the page when the request expects one (no `HX-Request`, `HX-Boosted`, or `HX-History-Restore-Request`). Do not put `hx-push-url` on a filter input — it would push the `/rows` URL.

**Column order (#1220).** Spec order in `registry.py` is the default column order, and every tab follows one rule: title, company, location, then the `SCORE` columns, then the rest (`tests/test_board_column_order.py` checks each tab). Action cells are not specs: `leading_cols` (Status, Reject) render before the spec columns and `trailing_cols` (the dashboard's exclusion Rule) after them, in both `_table_header.html` and `_job_row.html`. The `?cols=` list order is the user's order: `filters.url.ordered_specs(specs, parsed.cols)` returns the listed specs in that order, then the unlisted ones in registry order, and every board route passes `specs` through it, so the header, the rows and the Columns dropdown share one order. A row re-rendered by a board action (`board_actions._persisted_columns`) reads the tab's persisted view for the same reason.

Adding a new tab: declare ColumnSpec list in `registry.py`, add base WHERE + `_<tab>_query()` in `routes/board.py`, include `_filters.html` + `_table_header.html` in the template.

**Per-tab persistence (#277).** The framework's URL state persists per tab via the `view_prefs` SQLite table (migration 0005). Cascade for what filters/cols apply on load: **URL ?cols= + filter params > persisted `view_prefs` row > `ColumnSpec.default_visible`**.

Mechanism — redirect-on-cold-load + auto-save-on-URL-settle, both in `findajob.web.routes.board`:

- `_maybe_redirect_to_persisted(...)` — page GET with no allowlisted filter state but a persisted row 303-redirects to the same path with `?<persisted_qs>`. Bookmarks/deep-links win because the URL has filter state by the time this check runs.
- `_persist_view(...)` — every page + `/rows` GET auto-saves the serialized parsed filters via `findajob.web.view_prefs.save()`. Density and other unrelated URL params (`?dismiss_*=`) are filtered by construction — `view_prefs.serialize()` rebuilds the querystring from `ParsedFilters` after parsing, not from `request.url.query`. **Default-aware cols (#844):** when `parsed.cols` equals the tab's `default_visible` columns in registry order, the `cols=` clause is dropped from persistence so a no-op clause doesn't ride the cold-load redirect and render the chip-strip's cols pill on a perceived default view. Order counts (#1220): a reordered default set is a real preference and persists. A view saved before #1220 holds its `cols` in the old registry order by accident; migration 0013 marks such rows (`view_prefs.cols_ordered = 0`), `view_prefs.load()` puts their `cols` in the current registry order once and sets the flag, and `save()` always sets it.
- `POST /board/{tab}/reset-view` — explicit clear via the "Reset to defaults" link in `_filters.html` AND the "Clear all" link in `_active_filters.html`. 303s back to the bare tab URL.
- `POST /board/{tab}/reset-filter/{name}` — per-chip clear backing the ✕ buttons on the chip strip in `_active_filters.html` (#844). Reads the persisted state, removes the named key (a column name, the literal `cols`, or the literal `sort`), re-serializes with `default_cols`, and 303-redirects to the path with the remaining filters in the URL (or bare `/board/{tab}` if nothing remains). It is a POST rather than a GET anchor because a GET for the last remaining filter lands in `_maybe_redirect_to_persisted`'s cold-load branch and snaps back to the persisted state.

UI: the "Columns ▾" dropdown in `_filters.html` mirrors the enum-popover Alpine pattern from `_table_header.html` (a row per spec column in display order, each with a checkbox and ↑/↓ buttons; Apply/Clear/Cancel). ↑/↓ move the row in the DOM; Apply sends the checked names in row order, so the row order becomes the `?cols=` order. Apply loads the page with the new `?cols=` (`filters.js` `commitColumns`) instead of swapping only `#rows`, because the `<thead>` renders once per page load. Clear still swaps the rows through the hidden `cols` input (#1232). Adding a new tab to persistence: append the tab id to `view_prefs.ALLOWED_TABS`, the migration's CHECK constraint, the `_URL_TAB_TO_STORAGE` map (if the URL form uses a hyphen), and the `ensure_view_prefs_table()` test helper.

**Reject-reason order (#1220).** Every reject-reason dropdown on the board (the Jinja global `reject_reason_options()` in `app.py`: reject, change-reason and archive cells) shows one flat list ordered by `findajob.web.reject_reason_order`. Fit reasons come first, most-used first by `feedback_log` count, with ties in `reject_reasons.yaml` order. The bookkeeping reasons (`BOOKKEEPING_REASONS`: Already Applied, Stale/Closed, Company passed, Other, matched case-insensitively) come last, in YAML order. The counts are memoised for 30 s per database because the dropdown renders once per row; the reasons themselves are read fresh on every call (#490). The `reject_reason` filter chips keep the YAML order (`registry._reject_reason_values`).
